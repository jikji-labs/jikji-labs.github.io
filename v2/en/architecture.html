Design stage — before implementation

One control plane, distributed execution

The initial design assigns authoritative policy, sessions, scheduling and storage to one server. Workers pull bounded work assignments.

CLI / HTTP / MCP → Policy · Budget → Workers → Evidence

Execution path

CLI, HTTP and MCP requests pass through authentication, policy and budget checks, planning, local or remote execution, and safe observations, checkpoints and receipts. File reading, editing, search, isolated shell execution and an action-observation loop form the proposed tool contract. Local execution in the same binary is designed to preserve these policy boundaries.

Storage and failure boundary

SQLite and PostgreSQL target the same logical schema and contract tests. Remote workers do not access the server database directly. The design uses mTLS, leases and fencing epochs to reject stale results. The initial single server remains an availability boundary; high availability is not promised.

Provisional resource targets · unmeasured

Initial proposed targets are CLI startup p95 ≤25 ms, idle core RSS ≤32 MiB and a default stripped binary ≤15 MiB. Model, network and database initialization need separate measurement boundaries. Total cost must include the bridge, knowledge engine and tool processes.

All figures are provisional targets, not measurements. Korean is authoritative. Source: design documents 01–10, R1–R20; editorial snapshot 2026-10-18.
